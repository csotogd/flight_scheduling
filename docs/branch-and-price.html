Branch & Price & Cut, visually

How do you optimize over a trillion variables you never write down?

This is a visual guide to the algorithm inside this repository — an adaptation of Derigs & Friederichs (2013) — which plans a cargo airline's entire week: which flights exist, which aircraft flies each one, how the fleet rotates, and which shipment rides which itinerary. One model, solved together. Scroll; each idea builds on the previous one.

1The problem: four decisions, one week

A cargo airline's week is periodic: 10,080 minutes that wrap around from Sunday night back to Monday morning. Inside that loop, the airline must choose flights (some mandatory, some optional candidates), assign a fleet type to each, chain flights into rotations each physical aircraft can fly — visiting a maintenance base often enough — and route cargo from origins to destinations before deadlines, connecting through hubs.

Everything happens on one canvas: the time-space network. Airports are horizontal lanes, time flows to the right, flights are diagonal arcs, and waiting on the ground is a horizontal arc. Both aircraft and cargo live on this canvas — that's what lets one model decide everything at once.

The catch: decisions interact. The green shipment only moves if the purple aircraft (or a colleague) actually operates those flights; the purple rotation only pays off if enough green flows fill it. Optimizing them separately leaves money on the table — so we won't.

2The key idea: variables are stories, not switches

A naive model would use tiny variables — "does flight 217 exist?", "does shipment 4,182 use leg 88?" — and then need thousands of constraints just to keep the tiny decisions coherent (connectivity, timing, transfers, maintenance). ACSP-T does the opposite. Its variables are whole feasible stories, called columns:

Cargo path COLUMN

A complete, feasible itinerary for one O&D demand: legs + transfer stops, respecting availability time, delivery deadline, transfer minima, handling times, curfews. Variable xp = tonnes flowing on path p.

Flight string COLUMN

A complete, feasible work-week for one aircraft of one fleet: a chain of flights with turn times, returning to base, hitting an A-check within its interval. Variable ys = how many aircraft fly string s (integer).

Feasibility is baked into each column — an infeasible itinerary simply never becomes a variable. The model's constraints only need to arbitrate between stories: don't oversell capacity, don't use more aircraft than you own, cover every mandatory flight.

The price of this elegance: there are astronomically many feasible paths and strings — far too many to enumerate. The entire algorithm is a machine for working with that universe of columns without ever writing it down.

3The master problem: an LP that arbitrates

The Restricted Master Problem (RMP, in Rmp.cs) is a linear program over the columns generated so far ("restricted" = it only knows a tiny, growing subset of the universe). It maximizes profit — cargo revenue minus flying costs — subject to the paper's rows (14)–(22). Click each constraint family to see what it does:

Solving this LP yields two things: a plan (optimal values for the known columns) and — the real treasure — dual prices π on every row: what one extra unit of each shared resource is worth. A dual on a leg-capacity row says "a marginal tonne of lift on this leg is worth $310/t right now." Those prices are the language the next section speaks.

4Column generation: a conversation between an LP and two oracles

The RMP only knows a few columns — its optimum is a local truth. Are there better stories out there in the un-enumerated universe? To find out, we compute each hypothetical column's reduced cost: what it would add to profit at the current prices.

rc(path p) = revenue/t − Σ π_cap(legs of p) − π_dem(its O&D) − Σ π_cut rc(string s) = − operating cost(s) + Σ π over the flights s covers − π_fleet(its fleet) if rc > 0 for some column not yet in the RMP → adding it improves the LP if no such column exists anywhere → the LP optimum is PROVEN over all columns

Finding the best hypothetical column is the pricing problem — and here's the magic: it's a shortest-path problem on the time-space network, solvable without enumerating anything (§5). The loop below is the beating heart of the whole system. Step through it:

When both oracles come back empty-handed, we hold a certificate: no story in the entire universe improves this LP. Its value is now a true upper bound on any integer plan — that's what makes reported optimality gaps honest. And if the clock runs out mid-conversation, the Farley bound turns the best remaining reduced costs into a still-valid bound (the subtle in-master/at-upper-bound case is handled and tested — see FarleyBoundTests).

5Pricing: shortest paths through a priced world

PRICE-P — cargo paths A* + resources

For one O&D, imagine walking the time-space network from origin to destination. Each leg now has a toll: its capacity dual π_cap. The best new itinerary is the walk that maximizes revenue − tolls while respecting resources: the delivery deadline, transfer count, handling times. That's a Resource-Constrained Shortest Path Problem, solved with A* — an admissible estimate of the best possible remaining toll (h(v)) prunes hopeless prefixes, and dominance tests discard walks that are worse in both cost and remaining slack.

PRICE-S — flight strings labels over a multi-week DAG

Pricing an aircraft's work-week is harder: the walk must chain flights with turn times, wrap the periodic week, and fit an A-check within the maintenance interval. The pricer unrolls the periodic week into a multi-week DAG and runs a labeling algorithm: each label is a partial work-week carrying resources (elapsed time since maintenance, accumulated reduced cost). At each node, only the best σ = 20 labels survive (bucket ordering keeps them diverse rather than 20 near-clones).

This label limit is the algorithm's one honest approximation: without maintenance the string pricer is exact and so is the whole method; with maintenance, a provably-best string can occasionally be pruned — the same trade the paper makes (§9).

6Cuts: closing the fractional loophole

LPs love loopholes. The selection variable of an optional flight can sit at x = 0.4 — flying "40% of a flight" — and cargo happily books 40% of its capacity, revenue with almost no fixed cost. Real airlines can't fly fractional airplanes, so the LP bound is too optimistic. Implied-bound cuts (§8) add the missing logic: flow on a flight's legs can't exceed capacity times its selection. 7Branching: forcing integer answers, without breaking pricing

Cuts tighten, but the LP can still land fractional. Then we split the world in two and solve both halves — recursively. The art is what to branch on. Branching on a single column ("forbid path #4,182") is a disaster: the pricer would just regenerate its near-twin. Instead we branch on decisions the pricers can respect, implemented as visibility flags on the pricing graphs (PricingRestrictions):

Flight in / out

Left child: the optional flight exists (x=1). Right child: it never happened (x=0) — its legs vanish from both pricing graphs.

Fleet assignment

This flight is flown by fleet k — or forbidden to fleet k. The string pricer for other fleets simply loses the flight from its DAG.

Follow-on

The finest scalpel: after flight i, an aircraft must (or must never) continue directly to flight j. Prunes fractional rotations pair by pair.

8The big picture: three nested loops

Everything above — master, pricing, cuts, branching — is the paper's exact engine. This repository wraps it in two more loops that turn it into a network-design tool. Read the diagram inside-out:

Why this architecture wins

Feasibility by construction

Deadlines, curfews, handling, maintenance live inside the pricers — the master never sees an infeasible story, and an independent checker audits every incumbent anyway.

Honest bounds, always

Column generation proves LP bounds over the full column universe; the Farley bound keeps them valid under hard time budgets. Gaps you can put in front of a CFO.

Scale by locality

Only promising columns are ever materialized; eviction bounds the design-round model; consolidation and regional solves stretch the same engine to planet-scale instances.
